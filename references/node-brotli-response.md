# Node.js and Brotli decoder response

Use this procedure for Node.js runtime advisories or Brotli decoder incidents, including the issue nicknamed Node2Shell. Apply per-project permission, canonical-root checks and descendant exclusions first. Global version managers, shared tools, IDEs, CI runners, caches and remote services require their own named scope. Start with trusted static tools; do not run project JavaScript, imports, package-manager commands or downloaded vulnerability checkers to inventory a suspect environment.

## Identify the actual vulnerable implementation

Resolve the nickname to the CVE and primary advisory. Record the decoder implementation, affected release lines/builds, upstream fix identity, distributor backports and research timestamp. Fetch current [Node.js security notices](https://nodejs.org/en/blog/vulnerability) and relevant vendor advisories; this procedure intentionally has no fixed minimum-version table. The [October 2026 Node.js advisory](https://nodejs.org/en/blog/vulnerability/october-2026-security-releases) identifies CVE-2026-111497 in the bundled Brotli decoder. [Brotli's upstream release](https://github.com/google/brotli/releases/tag/v1.2.1) identifies the underlying library issue; consult [the CNA's CVE record](https://www.cve.org/CVERecord?id=CVE-2026-111497) for implementation and affected-branch criteria beyond Node.js. Track other fixes in the same runtime release separately; fixing one decoder path does not validate unrelated TLS, DNS, permission-model or framework flaws.

Establish runtime/build vulnerability and attacker-controlled decoder reachability as separate findings. A vulnerable runtime warrants upgrading even when no reachable path has yet been established. Decoder reachability alone does not prove a successful exploit or historical compromise. Distinguish vendor-confirmed impact, a research demonstration, observed crashes, and confirmed attacks; absence from an exploited-vulnerability feed is not clearance.

## Trace bytes to the decoder in both directions

For every approved service, tool or job, map input origin, transformation order, exact package/adapter version, decoder call, execution context and runtime/library build. Include dependency code and generated bundles; direct application imports are not the whole surface. Use these leads, then verify the actual selected version/configuration rather than assuming a package name enables decoding:

| Path | Investigation and common missed boundary |
| --- | --- |
| Inbound request parsing | JSON, raw, text and URL-encoded parsers, framework plugins and custom middleware may inflate `Content-Encoding: br`. Check parser version, content-type matching, `inflate` settings, route registration and middleware order. Parsing can precede authentication and the application handler. |
| Outbound HTTP response handling | Server-side `fetch`/Undici, Axios and other clients can decompress responses automatically. Trace redirects, SDK wrappers, downloads, webhook consumers and SSR/data-fetching jobs to the actual adapter and response-body handling. A response can be attacker-controlled even when the original URL is fixed or authenticated. |
| Remote image/content optimization | Self-hosted image optimizers and preview/import/proxy services may fetch and decode external responses before validating image/content bytes. Map configured origins, redirects, response decoding and serving runtime; inbound-only WAF protection does not establish coverage here. |
| Direct decoding outside HTTP | Follow asynchronous, synchronous, stream, iterable and wrapper APIs processing uploads, files, object storage, queues, cached/database blobs or build inputs. Trace aliases and native addons, not only literal `brotliDecompress` calls. |
| Linked or embedded decoder copies | Inspect separate runtime binaries, bundled native libraries, tools and platform artifacts. A project's patched Node executable does not replace another tool's embedded Node/Brotli or a differently linked decoder. |

Current [body-parser documentation](https://expressjs.com/en/resources/middleware/body-parser/) describes automatic Brotli inflation across its JSON/raw/text/URL-encoded parsers and an `inflate` option enabled by default. This does not describe every historical release: verify the resolved Express/body-parser combination, installed code and configuration. An older parser that rejects Brotli excludes that particular parser path, not other middleware or outbound decoding.

The [Undici Fetch implementation](https://github.com/nodejs/undici/blob/main/lib/web/fetch/index.js) and [Axios Node HTTP adapter](https://github.com/axios/axios/blob/v1.x/lib/adapters/http.js) demonstrate response decompression. Inspect the deployed versions rather than treating these moving source links as the deployed code. Raw `http`/`https`, Undici's different APIs, browser adapters and custom transports can behave differently. Do not assume advertising only `identity` prevents a client from decoding an unsolicited compressed response; verify the actual implementation. Do not invent a universal `fetch` option to disable decompression.

Trace header normalization and proxy transformations too. Where supported, combined/chained content encodings can still reach Brotli; interpret case, whitespace, repeated fields and streaming/chunk boundaries through the actual HTTP parser/client adapter and decoder pipeline. An edge rule matching only one literal header string is not evidence that all accepted paths are blocked. Do not assume every parser supports encoding chains.

The [Node zlib API](https://nodejs.org/api/zlib.html) includes `brotliDecompress`, `brotliDecompressSync`, `createBrotliDecompress` and, on relevant releases, iterable `decompressBrotli` APIs. Use terms such as `brotli`, `Content-Encoding`, `inflate`, client adapters and decoder bindings as search leads. Pure response compression, gzip/deflate decoding and WebSocket permessage-deflate do not by themselves establish this Brotli decoder path. Absence of a direct call or a package named `brotli` is equally insufficient to exclude it.

For a concrete framework example, inspect the deployed image-optimizer implementation and the [Next.js maintainer's Node.js bulletin](https://vercel.com/kb/bulletin/node-js-security-advisory). Framework upgrades or image origin allowlists do not independently prove the underlying runtime patched. Fetching must be traced even when the application has no Brotli request-body parser.

## Inventory every actual runtime and library build

Within each named scope, compare project runtime selectors, version-manager installations, service definitions, process executable identity, containers and all build stages. Include development servers, background jobs, serverless functions, packaged desktop/CLI tools and automation. A CI setup step that patches the application's Node version does not necessarily update the runner's separate JavaScript-action runtime. Inspect what ran during the incident window, not just today's mutable image tag.

Use exact runtime package/build, immutable binary/image identity and vendor patch evidence. A bundled library version string can remain unchanged after a security patch is cherry-picked; a higher library version string is not provenance. Conversely, a custom Node build may dynamically link a different system Brotli. Resolve actual linkage and exact distributor package revisions before applying upstream version conclusions. Unsupported runtime lines require migration or a verifiable vendor-supported fix, not comparison to an unrelated maintained major.

Investigate cross-language/native consumers when the upstream library profile warrants it: Python bindings, native addons, statically linked executables, clients built with Brotli support, and embedded browser/server runtimes are candidates. Verify implementation identity, linked/build version, patch and reachable decoding separately. A Rust crate or compatible runtime with a similar API/name may use a different implementation; do not classify it affected or fixed merely because Node was patched. Unknown vendor status stays unknown.

Do not bootstrap a suspect interpreter to collect `process.versions`. Execution probes require a trusted executable/host and reviewed startup configuration, including preload/import hooks and wrappers. A developer shell's `node --version` does not identify a running service. If trustworthy execution is unavailable, use static package/build/provenance records and report the remaining uncertainty.

## Patch and verify the effective boundary

Within local patch approval, update affected runtime selectors, image/build inputs, embedded binaries and applicable native libraries using current vendor fixes. Rebuild the artifacts that contain them. An `engines.node` declaration, `npm audit` result or application dependency update does not replace the engine. Verify all old copies and architectures relevant to the approved deployment.

If a runtime patch cannot be activated immediately, document temporary controls by path. Rejecting Brotli request bodies before any decoding, or a verified parser setting such as `inflate: false`, can reduce a specific inbound path. Check direct backend access, alternate listeners and middleware order. Stripping `Content-Encoding` is not a verified safe substitute. Inbound WAF rules do not cover fetched responses, local files, queues or other decoder callers. Output-size limits, authentication after parsing, TLS transport and catch/try handling are not proof against native memory corruption. Disabling outbound decompression must be validated for the actual client and all downstream/manual decoders, including compatibility impact. Confirm behavior changes fall within existing authorization; obtain approval for additional scope.

Obtain separate authorization for deployments, service changes, draining/restarts and remote probes. After activation, verify actual serving/worker builds and all replicas against immutable artifacts; installed files and successful health checks do not prove old processes exited. Test normal inbound parsing, allowed compressed responses, image/content fetching and background work relevant to the changed paths. Valid bounded compressed fixtures and positive controls test routing and compatibility. Keep malformed upstream regression fixtures in isolated, authorized patched instances; never send exploit/crash probes or decompression bombs to production. A single decoder error or crash is not a complete regression test or proof of code execution.

Record a path-by-path outcome: confirmed affected implementation and reachable decoder; affected build with reachability unresolved; exact verified fix/backport with activation evidence; or an explicitly unverified surface. No finite keyword search certifies every vector. If evidence suggests exploitation, follow the broader evidence-preservation, containment, credential-reachability and clean-recovery workflow; a runtime update alone does not clear a compromised host.
