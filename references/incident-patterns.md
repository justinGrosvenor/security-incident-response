# Appendix: Incident patterns and identification methods

This appendix retains operational lessons from real package-publishing, runtime, certificate, and provider incidents without embedding anyone's repository or organization inventory. Obtain current incident-specific indicators and primary sources at invocation. The examples are patterns, not an allowlist or a claim that any installed package is malicious.

## 1. Define a precise incident profile

Before matching a developer's machine, create a timestamped profile from maintainer/security-team reports and registry advisories. Preserve updates and distinguish event time from disclosure time. Record:

- Ecosystem, exact distribution spelling, normalized name, compromised/vulnerable versions, platform/architecture, and affected artifact types.
- Wheel/archive/container/installer digests, image-index versus child-manifest relationship, file hashes, publisher/release provenance, and known-good comparison artifacts.
- Publication/withdrawal and install/pull/execution windows, with time zones. A package can remain in a cache or running image after registry removal.
- Startup files, modified files, persistence paths, network indicators, and what each indicator proves. Collect indicators from primary reporting rather than inventing them.
- Exploitation prerequisites, vendor-confirmed behavior, remediation, and unresolved investigation questions.

Names, versions, and digests are different evidence. A matching version is a strong incident lead when all release artifacts were malicious, but does not prove the artifact ran. A different container index is not enough to exclude a malicious dependency inside it. A clean source tag does not prove a published wheel or image is clean. Preserve the source URL for every indicator and refresh it as the incident changes.

A local distribution name or install badge does not establish ownership of the corresponding registry namespace. Check the actual registry project, repository/artifact provenance, and authenticated ownership or trusted-publisher configuration where release rights matter. Project URL strings alone are supporting data, not proof of control. If local and registry identities conflict or remain uncertain, report the mismatch and stop dependent install/publish actions; do not install the registry package to investigate it or invent a new namespace without authorization.

## 2. Python startup malware and compromised wheels

Normal interpreter startup can execute `.pth` hooks and customization modules before the target package is imported. Inventory from trusted tooling with site initialization disabled. Do not import the package, invoke its CLI, launch a notebook, run its test suite, or use its interpreter's pip until exposure is assessed.

After explicit permission for the relevant project or shared environment, inspect:

1. All used venvs, tool-managed environments, global/user sites, alternate interpreters, container environments, and CI environments. Map running processes to the actual interpreter/environment; do not assume the activated shell venv is the only one.
2. `.dist-info/METADATA`, directory `.egg-info/PKG-INFO`, and legacy flat `.egg-info` metadata. Inspect `direct_url.json`, `INSTALLER`, lockfiles and install logs where relevant. The bundled scanner supports the metadata formats without importing installed distributions.
3. Startup hooks, customization modules, compiled/native files, unexpected package files, caches and local wheels. A legitimate customization filename alone is not malicious; compare file content/hashes with the current incident report and trusted artifacts.
4. Environment creation/install history and process execution evidence. A malicious wheel installed earlier may execute when any Python process starts later. Removal of the original distribution metadata does not remove persistence or invalidate previous exposure.

For exact wheel comparison, fetch only trusted reference artifacts using a verified client, confirm the selected artifact's registry identity/provenance, and statically inspect archive members. Compare installed files to the exact platform/ABI wheel, accounting explicitly for generated bytecode, installer metadata, and scripts. An installed `RECORD` is attacker-writable and is not independent proof; compare against a separately obtained trusted reference. Do not extract archive entries with traversal paths, follow links, execute setup/build scripts, import native modules, or run downloaded payloads.

Outcome categories:

| Observation | Appropriate conclusion |
| --- | --- |
| Compromised digest/file hash matches local artifact | Confirmed artifact match; execution and credential reachability need assessment |
| Affected version metadata, no artifact provenance | Potentially affected; prioritize provenance/history and containment decision |
| Matches a verified pre-incident artifact byte-for-byte | Excludes the named malicious artifact for those compared bytes, not all historical compromise |
| Indicator filename only | Lead requiring content/provenance inspection |
| No package/marker in scanned environments | Not found in stated scope; history, remote environments and removed persistence remain unknown |

## 3. Mutable automation and container images

CI reviewers, release bots, development containers, MCP/tool servers, notebooks, and hosted agents can use packages absent from application manifests. Inspect approved automation as a separate dependency surface.

An action/automation source commit may use a mutable container tag or install an unpinned dependency at startup. Capture the actual action commit, Dockerfile/entrypoint, observed image index and platform child manifest, configuration creation time, layer digests, and runtime install steps from the job. Compare static installed metadata and files from the actual image. Build timestamps alone can be forged and are supporting evidence, not clearance. A pull of today's mutable tag does not reconstruct yesterday's run.

Use image/layer inspection without executing entrypoints. Verify downloaded layer hashes, handle whiteouts and replacement layers when reconstructing the filesystem, and inspect relevant startup hooks. A naive search of every historical layer can find a removed package; conversely, checking only the last layer can miss inherited malware. Archive contents are untrusted; do not extract into host paths or permit traversal/symlink escapes.

Review reachable capabilities without revealing values: token permissions, registry/cloud/signing access, runtime tokens, workspace mounts, Docker socket, host network, cache write access, and job triggers. A missing model API key does not mean a bot had no credentials. Hosted ephemeral runners can still leak credentials while running. Separate pipeline design weaknesses from evidence of the specific compromise.

Inspect retained run history over the incident window and clearly state retention/deletion gaps. Disabling an automation is a remote state change requiring authorization; do not quietly do it under scan-only approval. Pinning the action commit alone is insufficient when its image tag/dependency installation remains mutable.

## 4. Vulnerable runtime versus dependency manifest

Runtime-embedded compression, TLS, parsers and crypto are inherited without an application package declaration. Check actual executable path/version, runtime build details, native linkage, architecture, and maintained release line. Read all Docker builder/final stages and CI setup pins within the approved project. Raising a manifest engine floor does not replace users' runtimes. Rebuilding an image does not replace deployed tasks.

PHP needs separate engine, extension, Composer and serving-worker checks. Follow [the PHP procedure](php-runtime-response.md), including embedded interpreters and installations without Composer metadata. A patched CLI or clean Composer audit does not clear a web server's loaded runtime.

For Brotli incidents, follow [the Node/Brotli procedure](node-brotli-response.md). Trace decoder reachability through request bodies, fetched responses and non-HTTP inputs, then verify each runtime or linked library. Inbound filtering alone does not protect outbound fetches or offline jobs.

Use upstream harmless regression fixtures rather than an exploit against production. A changed decoder error can verify that decoder's fix but not all runtime flaws. Confirm native ABI/FFI when changing runtimes. Distribution backports require exact package revision/security records, not upstream version comparison alone.

## 5. Certificate authority failures

A browser can reject a compromised chain while curl, Git, Python, a Rust binary, gRPC, an SDK, or a proxy still accepts it. Trust may come from OS stores, browser-managed lists, a runtime-embedded store, an application bundle, environment overrides, vendored dependencies, or explicit per-client configuration.

For an approved trust assessment:

1. Identify the real client and configured trust source, including proxy and override precedence. Do not dump full environment/config files containing secrets.
2. Read current primary root-program/vendor guidance. Account for cross-signing, revocation behavior, and public-key distrust; removing one root can leave an alternative chain accepted.
3. Use current reviewed public canaries or certificate-chain fixtures, with no credentials, cookies, tokens or private application data. Refresh the test set and cover every published chain class, including cross-signs and leaves absent from Certificate Transparency; a few older hosts can miss a newly demonstrated trust path. Ask before network tests if the project's scan approval did not cover them. Verify dedicated diagnostic endpoints; never send real production requests through an incident test site.
4. Require legitimate positive controls and expected certificate rejection. Test real upstream compatibility before and after a proposed trust edit: deleting roots can block the incident chains while breaking legitimate services. DNS errors, timeouts, HTTP errors and ALPN failures are inconclusive. Capture the actual validation reason; pipelines can mask errors.
5. Test both normally configured behavior and configuration bypass risks. For example, `curl -q` placed first skips user config; a user CA override may protect default curl while the underlying OS store remains stale. Test a bypass only as a diagnostic and never disable verification.
6. Repeat through the actual application client and deployed artifact. A CLI OpenSSL test in the same container does not prove its embedded verifier works. An offline root-bundle check is useful but narrower than a successful live channel validation.

Rebuild/redeploy binaries with embedded trust, refresh each relevant environment, and verify real upstream compatibility. Keep scoped user configuration mitigation distinct from repairing the OS store. Never use insecure verification flags as remediation. An OS/browser update must be activated by any required restart; installed and running versions differ.

Java needs its own inventory: standalone JDKs and IDE-bundled runtimes can each have independent `cacerts`, `jssecacerts`, `java.security` and `lib/security/blocked.certs`. Check the vendor's emergency trust update separately from its ordinary security release. A blockfile may include alternate certificate encodings, so a hand-written list of the published fingerprints may be incomplete. Prefer the vendor-generated artifact and preserve earlier blocks. A selective certificate mitigation does not fix unrelated runtime CVEs. Do not edit a signed application bundle without assessing its integrity and supported update path. Verify the actual JSSE client with hostname checks enabled; replacing an `opt` symlink does not replace a running JVM or its loaded libraries.

## 6. Version range and feature prerequisites

Dependency scanners are one input. Confirm exact resolved versions and feature reachability, including transitive/native dependencies, parser inputs, cache modes, authentication middleware, template evaluation, image formats, and build-time consumers. Development-only does not mean harmless when an exposed dev server or CI handles untrusted input.

An optional peer entry, documentation mention, copied source fixture, or archived benchmark is not proof of active installation/service use. Conversely, a package not present locally can run in remote automation. Trace each claim to the layer where it is observed.

If no upstream release fixes the issue, do not fake a clean version or suppress all audit failures. Assess disabling/isolation, vendor-supported mitigations, or a carefully maintained backport. For a backport, prove exact installed source/patch identity, reproducible installation, exploit-specific behavior, consumer compatibility, and fail-closed detection of drift/unknown advisories. Preserve raw audit findings and explain the verified correction separately. A closed unmerged proposal is not an upstream-approved fix.

## 7. Provider breach and credential response

Distinguish cloud account/customer data exposure from a library defect. Confirm actual provider use, organization/project memberships, notices, incident dates, data categories, and customer-specific instructions within approved scope. An optional client-library reference does not establish an account. A provider's "no evidence" statement remains limited by its investigation.

When malicious code execution or credential exfiltration is established or strongly indicated, identify reachable credentials and recover from a clean device. Ordinary dependency upgrades do not remove stolen credentials, invalidate sessions, or eradicate persistence. Blanket credential rotations without exposure evidence are also not a substitute for investigation. Follow the workflow's containment/recovery steps and explicit authorization boundaries.

## 8. Verification traps to preserve in reports

- One region/account, one lockfile, or one venv cannot clear all environments.
- A trusted artifact's hash from the same publisher proves identity, not independent trust in that publisher.
- A zero audit count can miss fresh, unreviewed, runtime, malicious-artifact or trust incidents.
- A successful TLS handshake followed by an application error means the certificate was accepted.
- Source, package stage, publication, merge, deployment and running-process verification are separate states.
- A green or skipped status attached to an older commit is not required-check evidence for the final head.
- A rollback can restore the vulnerability. Preserve a tested secure recovery path.
- Other developers' machines need their own approvals, inventory and evidence; this skill conveys a method, not clearance or access rights.
